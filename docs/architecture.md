# ImageLab: architecture & conventions

Read this first when working on the repo (it is also the agent context that
`CLAUDE.md` imports). It explains how the code is organized and the rules to
follow. Other docs: [README](README.md) (what it is, commands) and
[deployment.md](deployment.md) (GitHub Pages).

## What this is

A personal web app of image tools. It is a **static site with no backend**:
everything, including OCR, SVG tracing and AI upscaling, runs in the browser,
mostly in Web Workers, with WebAssembly for what browsers can't do natively.
It is hosted on GitHub Pages and works offline once loaded. Keep solutions
simple and proportionate to a personal project: no servers, no containers, no
CI beyond the deploy workflow.

## Repository map

```
index.html              # Vite entry; applies the saved theme before first paint
vite.config.ts          # build + Vitest projects (unit: Node, browser: Chromium)
scripts/assets.mjs      # copies OCR files into public/vendor, downloads the model
public/                 # served as-is: logo, manifest, service worker (sw.js)
  vendor/  models/      # generated by `npm run assets` (gitignored)
.github/workflows/      # pages.yml: build + deploy to GitHub Pages (one job)
docs/
src/
  core/                 # pure TypeScript: no DOM, no Svelte; unit-tested in Node
  ops/                  # one file per operation (schema + run), plus the registry
  engine/               # the image engine: canvas, decode, encode, pipeline, worker
  app/                  # app state (Svelte runes): session, recipes, router, tools
  ui/                   # Svelte components
  main.ts  styles.css
```

## Layers and the dependency rule

Imports only point downward:

```
ui/            Svelte components (pages, forms, preview, results)
app/           state: session, recipes, router, tool presets, downloads
engine/        workers, decode/encode, pipeline runner, main-thread client
ops/           operations: settings schema + run(OffscreenCanvas) → result
core/          pure logic: schemas, recipe model, geometry, pixels, metadata, OCR, zip
```

`ops/` uses `engine/canvas.ts` (OffscreenCanvas helpers), and
`engine/pipeline.ts` uses the `ops/` registry. Logic that needs neither a
canvas nor the DOM belongs in `core/`, with a `*.test.ts` next to it.

## The core idea: operations, recipes, one export

- **An operation** (`ops/op.ts`) declares its settings with the schema builders
  in `core/params.ts` (`p.number`, `p.choice`, `p.boolean`, `p.color`,
  `p.custom`) and a `run` over `OffscreenCanvas`. Kinds:
  - `map`: one image in, one image out;
  - `combine`: all images in, one out (merge);
  - `svg` and `text`: terminal steps, producing SVG markup or OCR text, so
    nothing can follow them.

  The schema produces the defaults, validates values restored from storage
  (`sanitize`), and drives the generated form (`ui/ParamForm.svelte`):
  `when` hides a field, labels can depend on other values, and `custom`
  values get their own editor (the crop box).

- **A recipe** (`core/recipe.ts`) is a list of steps (`{op, params}`) plus the
  **export settings** (`EXPORT_PARAMS`: format, quality or target size, ICO
  size). Images stay decoded between steps; encoding happens once, at the end.
  The `keep` format ("original file, metadata removed") exists only without
  steps, and strips metadata losslessly (`core/metadata.ts`).
- **A tool** (`app/tools.ts`) is a preset recipe shown on the home page.
  Users can change any tool's steps, and save recipes of their own
  (`app/recipes.svelte.ts`). Last-used settings are kept per tool in
  localStorage and sanitized against the current schemas when read back, so
  renamed or removed settings never break the app.

To **add an operation**:

1. create `src/ops/<id>.ts` with `mapOp` / `combineOp` / `svgOp` / `textOp`;
2. add it to `OPS` in `src/ops/index.ts`, which makes it appear in "Add a step";
3. if it deserves a home-page entry, add a preset to `TOOLS` in `app/tools.ts`;
4. if its icon is new, add it to `ui/Icon.svelte`;
5. put pure math in `core/` (with tests), and add an engine test.

Rules for `run`:

- **Scale pixel settings by `context.scale`.** The live preview runs the same
  operation on a downscaled copy, so anything given in pixels (margins, blur,
  target sizes, gaps) must be multiplied by `context.scale` (1 for exports).
- Operations may edit their input canvas in place, so the pipeline never hands
  them a cached image.
- Throw an `Error` with a user-facing message for bad input. Mark slow ML
  operations `heavy`: they run one file at a time, and the preview stops
  before them.
- `check(size, values)` reports problems before running (e.g. too large to
  upscale), and the file list shows them.

## The engine

- **`engine/worker.ts`** runs everything: `inspect` (size, type, metadata,
  thumbnail), `process` (one file, or all files when the recipe merges),
  `preview` and `sample` (the color under a click).
- **`engine/client.ts`** (main thread) keeps a pool of up to 4 long-lived
  workers, so loaded models stay warm, plus one dedicated preview worker, so a
  slider drag never waits behind a batch. Cancelling terminates the worker:
  that's the only way to stop WASM mid-run. `app/previewer.ts` makes preview
  requests latest-wins.
- **`engine/pipeline.ts`** runs a recipe. Steps before a merge run per image;
  steps after it run on the merged image. Every output carries a small WebP
  `thumbnail`: the results list shows those, never the full-size files, which
  would each be decoded at full size.
- **Previews** run the steps before the first heavy/terminal one
  (`stopsPreview` in `ops/op.ts`). Each file is decoded once into a copy of at
  most 1600 px (the 8 most recent are kept); every preview size, the crop
  editor's and the color picker's are scaled down from it. Components ask for
  a new preview only when the previewed steps or the files shown change (the
  crop editor ignores its own crop box).
- **Decode** (`engine/decode.ts`): the browser's decoder, which applies EXIF
  orientation, for everything it can open. HEIC/HEIF goes through libheif
  (WASM) otherwise. The real type is sniffed from the bytes (`sniffType`), not
  trusted from the file.
- **Encode** (`engine/encode.ts`): JPEG/WebP/AVIF via `@jsquash/*` (the same
  output in every browser), PNG via `convertToBlob`. "Same format" keeps the
  input's format, except a JPEG that gained transparency becomes PNG; explicit
  JPEG flattens onto white. Target sizes binary-search the quality (PNG: the
  dimensions).

## The UI

- One page per tool (`ui/Workspace.svelte`): images, steps, export and the run
  button on the left; preview / results on the right (stacked on phones). No
  step-by-step routes. The left column reads as a pipeline (Input → Step n →
  Output, `ui/CardHead.svelte`) joined by a dashed connector that flows while
  a batch runs; the run button sticks to the bottom of the screen.
- Images can be dropped anywhere (`ui/DropOverlay.svelte`, which ignores the
  file list's own drag-to-reorder) or pasted, on any page, including home.
- `app/session.svelte.ts` holds the files, the recipe being edited, and the
  results, so files survive moving between tools and a batch keeps running
  while you browse. Results are marked out of date when the files or settings
  change after a run.
- Routing is hash-based (`#/tool/<id>`, `#/recipe/<id>`) so it works on
  GitHub Pages without rewrites.
- Object URLs are owned by components (`ui/BlobImage.svelte` creates and
  revokes them), never by the state.
- "Download all" builds the ZIP from the result Blobs themselves
  (`core/zip.ts` returns the archive as parts around them), reading one file
  at a time for its checksum, so a large batch is never copied into one
  buffer.

### Look and feel

- **Design tokens** live in `src/styles.css`, each color defined once with
  `light-dark()`. The page follows the system theme; the header's switch
  (`ui/ThemeSwitch.svelte`, state in `app/theme.svelte.ts`) can force light or
  dark by setting `data-theme` on `<html>`, which forces the `color-scheme`.
  An inline script in `index.html` applies the saved choice before the first
  paint (keep its storage key in sync with `theme.svelte.ts`). Switching
  reveals the new theme in a circle from the button (View Transitions). The
  light theme uses soft teal-tinted neutrals; the dark one plain charcoal
  greys, so the accent and the tool hues are the only color. Fade colors with
  `color-mix(in srgb, …, transparent)`: in OKLCH the mix drifts toward red.
- **Every tool and operation has a hue** (`ui/hues.ts`, keyed by icon), shown
  on its icon tile (`ui/Tile.svelte`, the `.tile` class) on the home page, in
  the workspace and in the "Add a step" menu. A new icon needs a hue there.
  The brand teal is for input, output and saved recipes.
- **Fonts:** Bricolage Grotesque (bundled from `@fontsource-variable`, so it
  works offline) for headings, the system font for everything else.
- **Motion** is short and eased, and honors `prefers-reduced-motion`: CSS
  animations and transitions through the reduced-motion rule in
  `styles.css`, Svelte transitions by taking their durations from
  `ui/motion.ts` (`ms(...)`).

## Cross-file invariants (easy to break)

- **Runtime assets aren't in git.** `scripts/assets.mjs` (run by `predev`,
  `prebuild`, `pretest`) copies the Tesseract worker, the LSTM-only WASM cores
  and the language data from `node_modules` into `public/vendor/`, and
  downloads the Real-ESRGAN weights from the repo's `models-v1` release
  (pinned by sha256) into `public/models/`. Code loads them through
  `RunContext.asset(path)`, which resolves against the app's URL.
- **OCR languages are listed twice:** `OCR_LANGUAGES` in `src/core/ocr.ts`
  and `scripts/assets.mjs`; each language also needs its
  `@tesseract.js-data/<code>` package.
- **The other WASM modules are bundled by Vite** through `new URL(...,
import.meta.url)`. Keep them in `optimizeDeps.exclude` (vite.config.ts), and
  pass VTracer its `.wasm` URL explicitly (its default file name is wrong).
- **Relative base (`base: './'`)**, so the build works under
  `/ImageLab/` on GitHub Pages and at any other path. Use relative URLs for
  public files.
- **No cross-origin isolation:** GitHub Pages can't send COOP/COEP headers, so
  WASM runs single-threaded (onnxruntime's CPU fallback, AVIF encoding).
  WebGPU is unaffected.
- **The theme's storage key** (`imagelab:theme`) is read both by the inline
  script in `index.html` and by `app/theme.svelte.ts`.
- **The service worker** (`public/sw.js`) caches everything same-origin. Bump
  `CACHE` if its strategy changes.

## Commands

```bash
npm run dev      # Vite dev server on :4200 (prepares assets first)
npm test         # unit tests (Node) + engine tests (headless Chromium)
npm run build    # svelte-check (no warnings allowed) + vite build → dist/
npm run preview  # serve dist/ locally
npm run format   # Prettier
```

## Conventions

- Svelte 5 with runes (`$state`, `$derived`, `$effect`, `$props`); shared state
  lives in `*.svelte.ts` classes under `app/`. TypeScript strict.
- Every module and component starts with a short comment saying what it is;
  comment the _why_ of anything non-obvious, not the _what_.
- Tests live next to the code: `core/**/*.test.ts` run in Node;
  `engine/**/*.test.ts` run in Chromium (Vitest browser mode) and exercise the
  real operations, codecs and WASM modules. Keep new pixel/geometry math pure
  and tested.
- Prefer native browser APIs (Canvas, `createImageBitmap`). Add a WASM
  dependency only for what the browser can't do or does inconsistently.
- Formatting: Prettier (100 columns, single quotes, `prettier-plugin-svelte`)
  and `.editorconfig`. All text files are LF (`.gitattributes`).
- **Always use the latest stable version** of the tools and packages in use
  (npm dependencies, Node.js, GitHub Actions). Dependencies are pinned exactly
  (`--save-exact`). Stay behind only for a hard, documented reason, recorded
  here. Today: TypeScript 6.0, not 7, because `svelte-check` supports only
  TypeScript ≤ 6.
- **Always commit and push after a change.** One commit per coherent change:
  don't flood the history with tiny commits, but don't bundle unrelated
  features or fixes together either. Commit messages follow conventional-commit
  style (`feat:`, `fix:`, …), in the imperative. A push to `master` deploys
  (unless it only touches docs).
- **Keep the docs in `docs/` up to date in the same change as the code**,
  without waiting to be asked. Check every doc the change could affect (the
  README's tool list and formats, this file's structure and rules,
  `deployment.md`), not just the lines that name what changed.
